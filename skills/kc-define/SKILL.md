# 제품 정의하기

사용자와 필요한 만큼만 대화하여 무엇을 왜, 누구를 위해, 어떤 상황에서 만들지 결정한다. 아이디어를 억지로 확정하거나 일반적인 화면 패턴으로 빈칸을 채우지 않는다. 이 스킬에서는 코드를 구현하지 않는다.

## 진입 상태 판정

입력 내용을 먼저 다음 세 가지 상태 중 하나로 분류한다.

### 아이디어가 없는 상태

- 사용자의 업무, 역할과 반복되는 불편을 먼저 확인한다.
- 사용자가 실제로 겪는 문제를 찾을 수 있도록 정보 탐색·신청·비교·추적 같은 업무 패턴이나 저장된 [예시 프로젝트](references/example-projects.md)를 보여줄 수 있다.
- 예시나 제안은 가설로 표시하고, 사용자가 선택하거나 수정하기 전에는 사실이나 제품 방향으로 확정하지 않는다.

### 일부 맥락만 있는 상태

- 이미 알려진 내용은 반복하지 않고, 사용자·핵심 과업·완료 결과·사용 환경·범위 중 구현 방향을 바꾸는 빈칸만 질문한다.
- 아이디어를 제품 문제와 한 가지 핵심 흐름으로 좁힌 뒤 부족한 UX 결정을 확인한다.

### 아이디어가 명확한 상태

- 바로 화면이나 코드를 제안하지 않고 정의 충분성 검사를 먼저 한다.
- 사용자·업무 맥락·역할 차이·핵심 과업·IA·정보 우선순위·상태 가시성이 충분하면 질문을 늘리지 않고 제품 정의나 PRD로 정리한다.
- 중요한 빈칸이 있으면 해당 내용만 질문하고, 이미 확정된 방향을 다시 발굴하지 않는다.

세 상태 모두에서 질문은 구현 결정을 바꾸는 내용만 고르며 한 번에 최대 세 개까지 묻는다. 사용자가 IA·사용성·시인성 같은 용어를 알 필요는 없도록 업무 언어로 질문한다.

## 정의 충분성 검사

PRD를 확정하기 전에 다음 항목을 확인한다. 핵심 항목이 비어 있으면 임의의 일반적인 앱 구조로 채우지 말고 질문한다. 위험이 낮고 제품 방향을 바꾸지 않는 기술 세부사항은 가정으로 표시하고 합리적으로 둘 수 있다.

- **사용자:** 가장 먼저 사용할 주요 역할과 보조 역할
- **업무 맥락:** 언제·어디서·어떤 기기로·얼마나 자주·얼마나 급하게 사용하는지
- **핵심 과업:** 사용자가 시작하는 행동, 입력, 제품 처리와 확인 가능한 결과
- **역할 차이:** 요청자·담당자·관리자처럼 서로 다른 과업과 화면이 필요한지
- **IA:** 사용자가 찾거나 비교해야 하는 정보의 묶음, 진입점과 이동 경로
- **사용성:** 다음 행동, 입력 오류, 빈 결과, 충돌, 권한 거부와 복구 방법
- **정보 우선순위:** 첫 화면에서 먼저 보여야 하는 정보와 보조 정보
- **상태 가시성:** 긴급·지연·위험·완료·확인 중 상태를 어떻게 구분하고 강조할지
- **환경·접근성:** 모바일·현장·저조도·터치·키보드·용어 이해도 등 관련 제약

상세 질문 예시는 [사용자·업무·UX 맥락 점검표](references/ux-context-check.md)를 참고한다. 질문 답변이 실제 업무 사실인지 사용자의 가정인지 구분해 기록한다.

## 진행

1. 제품 정의에 영향을 주는 현재 컨텍스트와 제공된 자료를 파악하고 입력 상태를 판정한다.
2. 아이디어가 없으면 업무 문제를 찾고, 일부 맥락이면 핵심 흐름으로 좁히며, 명확한 아이디어면 정의 충분성 검사를 먼저 수행한다.
3. 실제 사용자, 반복되는 문제, 핵심 행동과 관찰 가능한 완료 결과를 찾는다.
4. 사용자·업무 환경·역할별 과업·IA·정보 우선순위·상태 가시성 중 구현 결정을 바꾸는 정보만 질문한다.
5. 필수 범위와 제외 범위를 구분하고, 확인된 사실·사용자 가정·에이전트 제안을 표시한다.
6. 개인정보, 회사 기밀, 저작권, 결제, 외부 연동과 공개 범위처럼 제품 방향에 영향을 주는 제약을 확인한다.
7. 플랫폼, 데이터 보관, 인증, 배포와 운영상의 제약은 기록하되 사용자가 지정하지 않은 프레임워크나 공급자를 제품 요구사항처럼 고정하지 않는다.

아이디어 예시가 필요할 때만 [예시 프로젝트](references/example-projects.md)를 보여준다. 사용자가 예시를 선택했을 때만 대응하는 샘플 PRD에서 문제 구조와 설계 방식을 참고해 새 문서를 작성하고, 샘플의 사용자·데이터·기술·접근 정책을 그대로 승계하지 않는다.

## 산출물

- 간단하고 불확실성이 낮으면 사용자·핵심 과업·첫 화면 우선순위·완료 결과를 포함한 짧은 제품 정의를 대화 또는 사용자가 원하는 파일에 남긴다.
- 여러 화면, 데이터, 권한, 외부 연동 또는 인수 조건을 구현자에게 전달해야 하면 `PRD.md`를 작성한다.
- 사용자가 PRD나 특정 형식을 요청하면 그 형식을 따른다.

상세 PRD가 필요하면 [PRD 기본 문서](assets/PRD.md)를 프로젝트의 `PRD.md`로 복사해 사용한다. 화면 상태, 데이터 규칙, 접근 범위, 외부 연동과 수용 시나리오 중 해당 제품에 필요한 항목만 남기고 구체화한다. 실제 자료 없이 예시가 필요하면 가상 데이터의 목적과 범위를 정의한다.

작성 후 미완성 자리표시자, 모호하거나 충돌하는 요구사항, 역할별 UX 차이의 누락, 구현 전에 결정해야 할 사항이 남았는지 확인한다. 핵심 사용자·핵심 과업·정보 우선순위가 확인되지 않았는데도 일반적인 대시보드·CRUD·메뉴 구조를 확정하지 않는다.

## 완료

해결할 문제, 주요 사용자와 사용 환경, 핵심 과업, 역할별 차이, IA·정보 우선순위·상태 가시성 결정, 필수·제외 범위, 남은 가정과 생성한 문서 위치를 보고한다.
