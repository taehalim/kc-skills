## 1. 제품 개요

반도체 생산설비에 알람이 발생했을 때 현장 작업자가 설비명·알람 코드·증상으로 가상의 과거 사례를 검색하고, 확인 순서와 담당 부서를 빠르게 찾는 정적 웹서비스다. 실제 설비 제어와 안전 판단을 대신하지 않는다.

이 제품은 제조 도메인을 모르는 사람도 이해할 수 있는 “사내 문제 해결 사례 검색”의 한 예다. 반도체 공장은 여러 단계의 공정과 다양한 생산설비로 운영되며, 설비가 평소와 다른 상태를 감지하면 화면에 알람 코드와 메시지를 표시한다. 사용자는 이 코드가 무엇을 의미하는지 외우는 대신, 과거에 같은 알람이 발생했을 때 무엇을 먼저 확인했고 어느 부서에 문의했는지를 검색한다.

이번 첫 번째 버전의 핵심 가치는 원인을 자동으로 맞히는 데 있지 않다. 흩어진 업무 지식을 검색 가능한 구조로 정리하고, 사용자가 필요한 사례를 빠르게 찾아 다음 행동을 결정하도록 돕는 데 있다.

## 2. 문제와 배경

### 업무 상황

가상의 반도체 공장 `한빛테크 1공장`에는 열처리, 세정, 검사, 이송 등 여러 공정이 있다. 여기서 공정은 제품이 완성되기까지 거치는 작업 단계를 뜻한다. 각 공정에는 온도, 압력, 위치와 센서 값을 감시하는 생산설비가 있고, 설정 범위를 벗어나면 `ALM-TEMP-021` 같은 알람 코드를 표시한다.

현장 작업자가 알람을 발견하면 바로 원인을 단정하지 않는다. 먼저 현장 안전 절차를 확인하고, 설비 화면과 주변 상태를 살핀 뒤, 과거 사례나 매뉴얼을 찾아 담당 부서에 전달한다. 그러나 실제 조직에서는 사례가 설비 매뉴얼, 교대조 인수인계 문서, 엑셀 이력과 메신저 대화에 나뉘어 저장되기 쉽다. 같은 문제가 과거에 해결됐어도 어느 문서에 있는지 몰라 처음부터 다시 확인하는 일이 발생한다.

특히 신규 작업자는 알람 코드만 보고 어느 공정과 설비의 문제인지, 무엇을 먼저 확인해야 하는지, 생산기술팀·설비기술팀·시설팀 중 어디에 문의해야 하는지 판단하기 어렵다. 숙련자는 개인 경험으로 해결하지만 그 지식이 시스템에 남지 않으면 담당자가 바뀔 때 다시 손실된다.

### 현재 업무 흐름

1. 작업자가 설비 화면에서 알람 코드와 메시지를 메모한다.
2. 현장 매뉴얼이나 공유 폴더에서 코드를 검색한다.
3. 결과가 없으면 이전 교대 기록과 메신저를 찾아본다.
4. 비슷한 사례를 발견하면 확인 순서와 담당 부서를 파악한다.
5. 찾지 못하면 숙련자나 여러 지원 부서에 문의한다.

이 과정은 자료의 위치를 아는 사람에게 의존하고, 검색 결과가 없을 때 “사례가 없는 것인지 검색어가 잘못된 것인지” 구분하기 어렵다는 문제가 있다.

### 제품이 바꾸려는 흐름

서비스는 제품에 포함된 가상의 알람 사례를 하나의 데이터 구조로 제공한다. 사용자는 알람 코드뿐 아니라 `온도`, `압력`, `카메라 응답 없음` 같은 일상 언어로도 검색하고, 공정과 해결 상태로 결과를 좁힌다. 상세 화면에서는 당시 현상, 작업자가 확인한 순서, 즉시 작업을 멈추고 현장 절차를 따라야 하는 조건, 담당 부서를 한 번에 확인한다.

### 데이터·운영 제약

실제 설비 정보와 사내 대응 절차는 기밀이거나 안전에 영향을 줄 수 있어 사용하지 않는다. 외부 사이트를 크롤링하지 않고 정적 JSON 파일을 사용하는 이유도 같다. 첫 번째 버전은 데이터 수집보다 “업무 사례를 검색 가능한 웹서비스로 구조화하는 기능”에 집중한다.

### 도메인 용어

| 용어 | 이 문서에서의 뜻 |
| --- | --- |
| 반도체 공정 | 제품을 만들기 위해 순서대로 수행하는 생산 단계. 이 예시에서는 열처리·세정·검사·이송으로 단순화한다. |
| 생산설비 | 공정 작업을 수행하거나 상태를 측정하는 기계와 장치다. |
| 알람 | 설비가 정상 범위를 벗어난 상태를 감지해 사용자에게 보여주는 코드와 메시지다. |
| 조치 사례 | 과거에 어떤 현상이 있었고 무엇을 확인했으며 어느 부서가 대응했는지 기록한 가상 이력이다. |
| 교대 기록 | 근무조가 바뀔 때 설비 상태와 미해결 문제를 다음 작업자에게 전달하는 기록이다. |
| 중단 조건 | 사용자가 임의로 계속 확인하지 말고 작업을 멈춘 뒤 현장 안전 절차와 담당 부서 안내를 따라야 하는 조건이다. |

## 3. 목표와 성공 기준

### 목표

- 작업자가 가상 알람 사례를 30초 안에 검색하고 필요한 확인 순서를 찾는다.
- 결과가 없을 때 검색 조건을 수정할 수 있다.

### 성공 기준

- 설비명·알람 코드·증상 키워드 검색과 공정·상태 필터가 함께 동작한다.
- 상세 화면의 설비·알람·확인 순서·담당 부서가 원본 데이터와 일치한다.
- 즐겨찾기가 새로고침 후에도 유지된다.

### 비목표

- 실제 장애 원인 진단, 설비 제어, 작업 승인과 안전 판단을 자동화하지 않는다.

## 4. 사용자

| 사용자 | 하려는 일 | 볼 수 있는 정보 | 할 수 없는 일 |
| --- | --- | --- | --- |
| 현장 작업자 | 알람 사례 검색·조회·즐겨찾기 | 가상 사례와 확인 순서 | 실제 설비 조작 |
| 교대 책임자 | 담당 부서와 이전 사례 확인 | 전체 가상 사례 | 사례 등록·수정 |

### 주요 사용자 시나리오

김지우 작업자는 열처리 공정에 배치된 지 한 달 된 신규 구성원이다. 설비 화면에 `ALM-TEMP-021`이 표시되었지만 코드를 외우고 있지 않다. 지우는 서비스에서 코드를 검색해 과거 사례를 열고, 즉시 중단 조건과 작업자가 확인할 수 있는 항목을 구분해서 읽는다. 이후 안내된 설비기술팀에 코드와 확인 결과를 전달한다.

박현수 교대 책임자는 다음 근무조에 미해결 알람을 전달해야 한다. 현수는 `확인 중` 상태만 필터링해 관련 사례를 찾고, 즐겨찾기에 저장한 뒤 인수인계 과정에서 다시 연다. 이번 버전에서는 새 사례를 등록하거나 내용을 수정하지 않는다.

## 5. 핵심 사용자 흐름

1. 사용자가 검색 화면을 연다.
2. `ALM-TEMP-021` 또는 `온도`를 입력한다.
3. `열처리` 공정으로 결과를 좁힌다.
4. 사례 상세에서 현상·확인 순서·중단 조건·담당 부서를 확인한다.
5. 사례를 즐겨찾기에 저장하고 저장 목록에서 다시 연다.

## 6. 기능 요구사항

### FR-1. 사례 목록과 검색

- 사용자는 제목, 설비명, 알람 코드, 공정, 발생 현상에 포함된 단어를 하나의 검색창에서 찾는다.
- 검색은 버튼을 따로 누르지 않아도 입력에 따라 결과를 갱신하되, 데이터가 적으므로 별도의 검색 서버는 만들지 않는다.
- 검색어의 앞뒤 공백, 영문 대소문자와 알람 코드의 대소문자는 결과에 영향을 주지 않는다.
- 각 결과 카드는 알람 코드, 설비명, 공정, 현상 요약, 발생일과 해결 상태를 보여준다. 사용자가 상세를 열기 전에 관련성을 판단할 수 있어야 한다.
- 수용 조건: `온도`, `temp`, `ALM-TEMP-021`을 각각 검색했을 때 해당 샘플이 포함되고 무관한 사례는 제외된다.

### FR-2. 필터와 정렬

- 공정과 사례 상태를 각각 또는 함께 적용한다. 검색어가 있는 상태에서도 필터가 추가로 적용되어야 한다.
- 활성화된 조건을 화면에 표시하고 `전체 초기화` 한 번으로 검색어와 필터를 제거한다.
- 기본 정렬은 최근 발생일 순이며 같은 날짜에는 제목 순으로 안정적으로 표시한다.
- 수용 조건: `온도` 검색과 `열처리`, `해결` 필터를 함께 적용했을 때 모든 조건을 만족하는 결과만 보인다.

### FR-3. 사례 상세

- 목록에서 선택한 사례의 설비·알람 코드·공정·발생일·상태를 그대로 표시한다.
- `무슨 현상이 있었나`, `먼저 무엇을 확인하나`, `언제 확인을 멈추나`, `어느 부서에 전달하나`, `과거에는 어떻게 마무리됐나`의 순서로 내용을 배치한다.
- 확인 절차는 번호 목록으로 제공하고, 중단 조건은 일반적인 확인 절차와 혼동되지 않도록 별도 경고 영역에 둔다.
- 수용 조건: URL로 상세에 직접 접근해도 올바른 사례가 보이고 존재하지 않는 ID에는 목록 복귀 행동이 제공된다.

### FR-4. 즐겨찾기

- 목록과 상세에서 같은 저장 상태를 공유한다. 어느 화면에서 저장하거나 해제해도 다른 화면에 즉시 반영된다.
- 같은 사례 ID는 한 번만 저장하며 저장 순서는 최근 저장한 항목이 먼저다.
- 브라우저 저장값이 손상됐거나 더 이상 존재하지 않는 ID가 있으면 앱이 멈추지 않고 해당 값을 제외한다.
- 수용 조건: 사례를 저장하고 새로고침한 뒤 `/saved`에서 열 수 있으며, 다시 해제하면 저장 목록에서 사라진다.

## 7. 화면과 상태

- `/`: 검색, 필터, 결과 수, 사례 카드
- `/cases/:id`: 사례 상세와 즐겨찾기
- `/saved`: 저장한 사례
- 빈 상태: `조건에 맞는 사례가 없습니다.`와 필터 초기화
- 데이터 오류: 기술 원문 대신 데이터 확인 안내

## 8. 데이터

정적 파일 `src/data/alarm-cases.json`을 사용한다.

| 필드 | 업무 의미 | 형식·예시 |
| --- | --- | --- |
| `id` | URL과 즐겨찾기에서 사례를 구분하는 값 | `case-temp-021` |
| `title` | 사용자가 결과에서 이해할 사례 제목 | `열처리 장비 온도 범위 초과` |
| `process` | 알람이 발생한 생산 단계 | `열처리` |
| `equipment_name` | 가상의 설비 이름 | `열처리 장비 1호` |
| `alarm_code` | 설비 화면에 표시된 가상 코드 | `ALM-TEMP-021` |
| `symptom` | 작업자가 실제로 관찰한 현상 설명 | `설정 온도보다 높은 값이 3분간 표시됨` |
| `occurred_on` | 과거 사례 발생일 | `2026-07-18` |
| `status` | 사례가 마무리됐는지 나타내는 값 | `해결`, `확인 중` |
| `owner_department` | 문의하거나 후속 확인할 가상 부서 | `설비기술팀` |
| `checks[]` | 작업자가 현장 절차 안에서 순서대로 확인한 가상 항목 | 문자열 배열, 최소 2개 |
| `stop_conditions[]` | 추가 확인을 멈추고 현장 절차를 따라야 하는 조건 | 문자열 배열, 없으면 빈 배열 |
| `resolution_summary` | 과거 사례가 어떻게 마무리됐는지 설명 | 해결되지 않았으면 현재 확인 상태 |
| `is_synthetic_sample` | 가상 데이터 여부 | 항상 `true` |

즐겨찾기는 `localStorage.savedAlarmCaseIds`에 ID 배열로 저장한다.

데이터 파일은 최소 12건으로 구성하고 모든 필수 필드가 있는지 TypeScript 타입 또는 런타임 검증으로 확인한다. `checks`와 `stop_conditions`에는 실제 현장 지시로 오인될 수 있는 상세 조작 명령을 작성하지 않는다.

## 9. 업무 규칙과 예외

- 모든 사례에 `가상 사례`를 표시한다.
- `stop_conditions`가 있으면 상세 상단에 먼저 표시한다.
- 해결되지 않은 사례는 `확인 중`으로 표시하고 해결된 것처럼 설명하지 않는다.
- 알 수 없는 상세 URL은 목록으로 돌아갈 행동을 제공한다.

- 외부 공개가 허용되고 요청된 경우 승인된 정적 호스팅 환경에 배포한다. 외부 서비스가 제한되면 로컬 실행까지만 구성한다.
- 즐겨찾기 외 사용자 데이터는 저장하지 않는다.

## 14. 화면 및 디자인 계약

### 14.1 제품 경험의 전제

이 제품은 설비 상태를 감시하거나 원인을 진단하는 관제 대시보드가 아니라, 작업자가 관찰한 사실로 과거 사례를 찾고 안전한 다음 행동을 결정하는 지식 검색 도구다. 첫 화면은 다음 질문에 빠르게 답해야 한다.

1. 입력한 알람 코드 또는 현상과 관련된 사례가 있는가?
2. 선택한 사례에서 추가 확인을 즉시 멈춰야 하는 조건은 무엇인가?
3. 작업자가 먼저 확인할 수 있는 항목과 전달할 담당 부서는 어디인가?

검색 결과 수, 중단 조건, 확인 순서와 담당 부서에 직접 기여하지 않는 정보는 첫 화면의 우선순위를 낮춘다. 존재하지 않는 실시간 설비 수치, 가동률과 공장 KPI를 만들어 관제 시스템처럼 표현하지 않는다.

### 14.2 정보 구조

- `사례 검색`: 검색어·공정·상태 조건, 결과 목록과 선택한 사례 상세를 제공하는 기본 작업 공간이다.
- `저장한 사례`: 교대 인수인계나 재확인을 위해 사용자가 저장한 사례만 같은 검색 구조로 보여준다.
- `사례 상세`: 독립 URL로 접근할 수 있으며 안전 판단과 전달에 필요한 내용을 정해진 순서로 보여준다.
- `이용 안내`: 서비스가 제공하는 참고 정보와 실제 현장 절차를 대체하지 않는 범위를 설명한다.

검색과 저장 목록은 별도 제품처럼 다른 레이아웃을 사용하지 않는다. 동일한 사례 객체와 동일한 상세 구조를 공유하고, 저장 여부만 목록 조건으로 반영한다.

### 14.3 대표 작업 화면

넓은 화면의 대표 작업 화면은 `검색 조건–결과 목록–사례 상세`가 한 작업 공간에 연결된 구조다.

1. 상단 검색 영역
   - 알람 코드, 설비명과 관찰 현상을 입력하는 통합 검색창을 가장 눈에 띄는 입력 요소로 둔다.
   - 검색창 주변에는 이 제품이 원인을 추측하지 않고 과거 사례를 찾는 도구임을 한 문장으로 설명한다.
2. 검색 조건 영역
   - 공정과 처리 상태 필터, 전체 초기화와 교육용 안전 안내를 둔다.
   - 빠른 공정 필터는 보조 탐색이며 검색창보다 강하게 강조하지 않는다.
3. 결과 목록
   - 알람 코드, 사례 제목, 관찰 현상 요약, 설비, 발생일과 처리 상태를 표시한다.
   - 사용자가 상세를 열기 전에 검색 의도와의 관련성을 판단할 수 있어야 한다.
   - 선택한 결과는 배경과 테두리 또는 위치 표시를 함께 사용해 명확히 구분한다.
4. 사례 상세
   - 선택한 결과와 같은 화면에서 읽되 목록과 상세의 경계가 명확해야 한다.
   - 상세 상단에는 알람 코드, 상태, 공정·설비와 저장 행동을 둔다.

### 14.4 사례 상세의 읽기 순서

상세 정보는 다음 순서를 바꾸지 않는다.

1. 알람 코드, 제목, 공정·설비와 관찰 현상
2. `즉시 중단 조건`
3. 담당 부서, 발생일과 현재 사례 상태
4. 작업자가 먼저 확인할 항목
5. 과거 사례의 마무리 결과
6. 담당 부서에 전달할 정보와 복사 행동

중단 조건은 일반 확인 절차보다 항상 먼저 노출하며 주의색, 아이콘과 `즉시 중단 조건` 텍스트를 함께 사용한다. 확인 절차는 번호가 있는 순서 목록으로 제공한다. 과거 결과는 현재 알람의 확정 원인이나 자동 권고처럼 표현하지 않는다.

### 14.5 모바일 전환

- 모바일 첫 화면에서는 검색창, 필터와 결과 목록을 먼저 보여준다.
- 결과를 선택하면 긴 목록 아래에 상세를 이어 붙이지 않고 목록 화면을 사례 상세 화면으로 전환한다.
- 사례 상세 상단에는 `목록으로` 행동을 항상 제공하며 선택 전 스크롤 위치 또는 검색 조건을 유지한다.
- 검색창, 필터, 저장과 목록 복귀 행동의 터치 영역은 최소 40px 높이를 확보한다.
- 모바일 전체 페이지에 가로 스크롤이 생기지 않아야 한다.

### 14.6 시각 체계와 시인성

- 밝은 중립 배경과 높은 명도 대비를 기본으로 사용한다. 어두운 산업 관제 화면을 모방해 본문 가독성을 낮추지 않는다.
- 짙은 남색은 구조와 주요 텍스트, 청록색은 검색 선택과 정상 상태, 황색은 확인 중과 안전 주의에 제한적으로 사용한다.
- 알람 코드에는 본문과 구분되는 고정폭 서체를 사용할 수 있지만 제목과 절차 본문은 읽기 쉬운 일반 서체를 사용한다.
- `해결`, `확인 중` 상태는 색상뿐 아니라 텍스트와 아이콘을 함께 표시한다.
- 산업 장비 사진, 실시간 그래프나 존재하지 않는 생산 수치를 임의로 생성하지 않는다.

### 14.7 상태와 피드백

- 입력에 따라 결과 수와 목록을 즉시 갱신하고 현재 적용된 검색 조건을 유지한다.
- 결과가 없으면 `사례 없음`과 `검색 조건 초기화`를 함께 제공한다.
- 손상된 즐겨찾기 값이 제외되어도 검색 화면은 정상적으로 표시한다.
- 존재하지 않는 사례 URL에는 빈 상세를 보여주지 않고 목록으로 돌아가는 행동을 제공한다.
- 저장과 해제는 목록과 상세에 즉시 같은 상태로 반영한다.

### 14.8 금지하는 화면 패턴

- 검색보다 통계 카드와 장식용 KPI를 먼저 보여주지 않는다.
- 사례를 마케팅용 카드 그리드로 배치하지 않는다.
- 중단 조건과 일반 확인 절차를 같은 강조 수준으로 섞지 않는다.
- 상세 정보를 여러 탭에 숨겨 한 사례의 안전 조건과 확인 순서를 오가게 만들지 않는다.
- 어두운 배경, 작은 고정폭 글자와 낮은 대비를 전체 화면에 적용하지 않는다.

### 14.9 UX 수용 기준

- 처음 방문한 사용자가 5초 안에 검색창과 검색 가능한 정보의 종류를 설명할 수 있다.
- `ALM-TEMP-021` 사례를 선택한 사용자가 추가 스크롤이나 탭 전환 없이 중단 조건을 먼저 발견한다.
- 결과 목록만 보고 코드, 설비, 관찰 현상과 상태를 구분할 수 있다.
- 모바일에서 결과 선택, 상세 확인, 저장과 목록 복귀를 가로 스크롤 없이 완료한다.
- 주요 본문과 제어 요소는 WCAG AA 수준의 색상 대비를 목표로 하며 상태를 색상만으로 구분하지 않는다.
