## 1. 제품 개요

배터리 연구소 구성원이 여러 팀이 함께 쓰는 고가 시험장비의 상태와 예약 시간을 확인하고, 중복 없이 이용을 예약하는 웹서비스다.

이 제품은 배터리 기술을 학습하는 서비스가 아니라, 수량이 적고 이용 시간이 긴 공용 자원을 여러 팀이 함께 사용하는 상황을 다룬다. 사용자는 장비 원리를 몰라도 “회의실보다 비싸고, 아무 때나 쓸 수 없으며, 다른 팀과 시간이 겹치면 안 되는 장비”라고 이해하면 된다.

첫 번째 버전에서는 실제 기업 시스템 전체를 복제하지 않고, 장비 조회부터 예약 검증·저장·취소까지 하나의 핵심 흐름을 완성한다. 단순한 입력 폼을 넘어 업무 규칙이 있는 예약 서비스가 목표다.

## 2. 문제와 배경

### 업무 상황

가상의 `새봄 배터리 연구소`에는 셀개발팀, 팩개발팀, 품질분석팀과 소재연구팀이 있다. 연구원들은 개발한 시료가 온도 변화나 진동을 견디는지 확인하거나, 충전과 방전을 반복했을 때 성능이 어떻게 달라지는지 시험한다. 이런 시험에는 고온·저온 환경 시험기, 충전·방전 시험기, 진동 시험기 같은 장비가 필요하다.

시험장비는 가격이 높아 팀마다 한 대씩 보유하기 어렵고, 한 번의 시험이 몇 시간 동안 이어질 수 있다. 따라서 여러 팀이 같은 장비를 예약해서 사용한다. 장비 운영자는 정기 점검이나 고장으로 사용할 수 없는 시간을 관리하고, 연구원은 자신의 시험 일정에 맞는 빈 시간을 찾아야 한다.

### 현재 업무 흐름

1. 연구원이 메신저에서 장비 담당자에게 사용 가능 시간을 묻는다.
2. 담당자는 공유 엑셀과 개인 일정을 확인해 답변한다.
3. 연구원이 이름·팀·시험 목적과 시간을 엑셀에 입력한다.
4. 다른 연구원이 거의 동시에 같은 시간을 입력하면 예약이 겹친다.
5. 장비가 갑자기 점검 상태가 되어도 예약자에게 즉시 공유되지 않을 수 있다.
6. 취소가 메신저에만 남으면 엑셀에는 예약이 계속 점유된 것으로 보인다.

이 방식에서는 “현재 화면에 비어 있다”는 사실이 예약 가능성을 보장하지 않는다. 두 사람이 동시에 제출할 수 있고, 저장 직전에 장비 상태가 바뀔 수도 있기 때문이다. 따라서 서버가 최종 저장 시점에 장비 상태와 시간 중복을 다시 확인해야 한다.

### 제품이 바꾸려는 흐름

연구원은 장비 목록에서 상태와 위치를 확인하고, 특정 날짜의 기존 예약을 본 뒤 빈 시간을 선택한다. 예약 폼을 제출하면 서버가 입력값, 장비 상태와 시간 겹침을 다시 검사한다. 조건이 맞을 때만 예약을 저장하고, 조건이 맞지 않으면 사용자가 수정할 수 있는 이유를 알려준다. 예약자는 완료 화면에서 한 번만 제공되는 충분히 긴 예약 취소 키를 안전하게 보관했다가 자신의 예약을 취소할 때 사용한다.

### 도메인 용어

| 용어 | 이 문서에서의 뜻 |
| --- | --- |
| 배터리 셀 | 전기를 저장하는 가장 작은 단위다. 이번 제품에서는 기술 구조를 구현하지 않는다. |
| 배터리 팩 | 여러 셀을 묶어 실제 제품에서 사용할 수 있게 구성한 단위다. |
| 시료 | 시험을 위해 준비한 가상의 배터리나 소재 샘플이다. 실제 시험 데이터는 저장하지 않는다. |
| 충전·방전 시험기 | 배터리를 반복해서 충전하고 사용해 성능 변화를 확인하는 장비다. |
| 환경 시험기 | 높은 온도나 낮은 온도 같은 환경을 만들어 제품의 상태를 확인하는 장비다. |
| 점검 중 | 정비·교정·고장 확인 등으로 예약할 수 없는 장비 상태다. |
| 예약 중복 | 같은 장비의 이용 시간이 일부라도 겹치는 상태다. |

## 3. 목표와 성공 기준

### 목표

- 연구원이 이용 가능한 장비와 시간을 확인하고 예약한다.
- 시스템이 시간 중복과 점검 중 예약을 차단한다.
- 운영자가 날짜별 예약 현황을 확인한다.

### 성공 기준

- 유효한 예약 한 건이 선택한 영구 저장소에 정확히 한 번 저장된다.
- 겹치는 예약, 잘못된 시간과 점검 중 장비는 저장되지 않는다.
- 새 예약이 장비 일정과 운영 목록에 반영된다.

### 비목표

- 실제 장비 제어, 사내 계정 연동과 시험 데이터 관리는 하지 않는다.

## 4. 사용자

| 사용자 | 하려는 일 | 볼 수 있는 정보 | 할 수 없는 일 |
| --- | --- | --- | --- |
| 연구원 | 장비 조회·예약·본인 예약 취소 | 장비 상태와 전체 예약 시간 | 타인 예약 취소 |
| 장비 운영자 | 전체 예약과 점검 상태 확인 | 예약 목적·사용자·시간 | 실제 장비 제어 |

### 주요 사용자 시나리오

이서연 연구원은 다음 주 화요일 오후에 고온·저온 환경 시험기를 두 시간 사용하려 한다. 장비 상세에서 화요일 일정을 확인해 13:00~15:00가 비어 있음을 보고 예약을 제출한다. 잠시 전에 다른 팀이 14:00~16:00를 먼저 예약했다면 서버가 충돌을 알려주고, 서연은 16:00 이후로 시간을 바꾼다.

최민호 장비 운영자는 아침마다 `/schedule`에서 당일 예약을 확인한다. 특정 장비가 점검 중이면 그 상태와 안내 문구를 확인해 문의에 답한다. 이번 버전에서는 운영자가 장비 상태를 수정하는 화면은 만들지 않고, 샘플 데이터와 DB 상태를 조회하는 데 집중한다.

## 5. 핵심 사용자 흐름

1. 연구원이 이용 날짜를 선택하고 장비별 시간표에서 여러 장비의 예약·점검 상태를 비교한다.
2. `고온·저온 환경 시험기 1호`의 비어 있는 `13:00~15:00` 시간 블록을 선택한다.
3. 선택 요약에서 장비·날짜·시간과 현재 충돌 여부를 확인한다.
4. 사용자명·팀·시험 목적을 입력해 예약을 제출한다.
5. 서버가 점검 상태와 시간 중복을 다시 확인하고 저장한다.
6. 완료 화면에서 예약 ID와 취소 토큰을 보관하고 장비 일정에서 새 예약을 확인한다.

## 6. 기능 요구사항

### FR-1. 장비 조회

- 첫 화면은 선택 날짜의 모든 장비를 행, 운영 시간을 열로 배치한 가용 시간표를 보여준다.
- 각 장비 행의 고정 정보 영역에는 장비명, 일반인이 이해할 수 있는 한 줄 용도, 위치와 현재 상태를 표시한다.
- 시간축에는 `예약 가능`, `예약됨`, `점검`을 서로 다른 시간 블록으로 표시하고 텍스트를 함께 제공한다.
- 사용자는 예약 가능한 시간 블록을 직접 선택해 장비·날짜·시작·종료 시간을 지정한다.
- `점검 중` 장비의 시간축은 점검 블록으로 표시하고 선택할 수 없으며 점검 종료 안내를 제공한다.
- 장비 분류 필터는 시간표의 장비 행을 좁히며 현재 표시 대수를 함께 갱신한다.
- 장비 정보가 더 필요하면 선택 요약 또는 `/equipment/:id`에서 용도, 위치와 운영 안내를 확인할 수 있다.
- 수용 조건: 점검 중인 진동 시험기는 모든 운영 시간이 선택 불가능한 점검 블록으로 표시되고 예약 정보 입력으로 진행할 수 없다.

### FR-2. 예약 신청

- 사용자명, 팀, 시험 목적, 이용 날짜와 시작·종료 시간을 받는다. 사용자가 직접 취소 비밀번호를 만들게 하지 않는다.
- 팀은 준비된 가상 목록에서 선택하고 시험 목적은 10~100자로 제한한다.
- 종료 시간은 시작보다 늦어야 하며 한 번의 이용은 최소 30분, 최대 8시간이다.
- 브라우저는 빠른 안내를 위해 먼저 검사하지만 서버가 같은 규칙을 다시 검사한다.
- 수용 조건: 필수값 누락, 잘못된 시간 범위와 너무 짧은 시험 목적은 DB 요청 전에 해당 입력 가까이에 표시된다.

### FR-3. 서버 예약 검증

- `POST /api/reservations`는 장비가 존재하는지, 사용 가능한 상태인지, 시간 규칙을 만족하는지, 기존 예약과 겹치는지 순서대로 확인한다.
- 모든 조건을 통과했을 때만 예약을 한 건 저장한다. 서버가 충분히 긴 무작위 취소 토큰을 생성해 hash만 저장하고, 원문 토큰은 예약 ID와 함께 성공 응답에서 한 번만 반환한다.
- 충돌 응답에는 다른 예약자의 개인정보를 포함하지 않고 `선택한 시간에 이미 예약이 있습니다`와 수정 행동만 제공한다.
- 클라이언트가 예약 시도마다 UUID 요청 키를 하나 만들고 서버와 DB가 고유값으로 검사한다. 버튼 비활성화뿐 아니라 같은 요청 키가 반복되어도 의도치 않은 중복 행이 생기지 않게 한다.
- 수용 조건: 13:00~15:00가 저장된 상태에서 14:00~16:00 요청은 거절되고 예약 수가 증가하지 않는다.

### FR-4. 예약 조회와 취소

- `GET /api/reservations?date=YYYY-MM-DD&equipmentId=...`는 화면에 필요한 시간·상태·시험 목적 요약만 반환한다.
- 예약 완료 화면에는 예약 ID, 장비명, 시간과 취소 시 필요한 안내를 보여준다.
- 취소 요청은 예약 ID와 취소 토큰을 받아 hash를 비교한다. 일치하면 상태를 `cancelled`로 변경하고 행을 삭제하지 않는다.
- 취소 endpoint에는 짧은 시간 안의 반복 실패를 제한하고, 존재하지 않는 예약과 틀린 토큰을 구분해 공격자에게 알려주지 않는 공통 오류를 사용한다.
- 이미 취소된 예약을 다시 취소하면 성공한 것처럼 중복 처리하지 않고 현재 상태를 안내한다.
- 수용 조건: 잘못된 취소 키에는 예약 내용이 변경되지 않고 올바른 키에는 일정에서 취소 상태가 반영된다.

### FR-5. 운영 현황

- 선택 날짜의 전체 예약을 시작 시간 순으로 보여주며 장비명, 이용 시간, 가상 사용자명, 팀, 시험 목적과 상태를 표시한다.
- 장비·팀·상태 조건을 조합해 필터링하고 결과 수를 표시한다.
- 운영 현황은 가상 공개 데이터임을 표시하며 실제 운영자 권한을 구현한 것처럼 표현하지 않는다.
- 수용 조건: 날짜와 장비를 선택했을 때 상세 일정과 운영 현황의 예약 수가 일치한다.

## 7. 화면과 상태

- `/`: 날짜별 장비 가용 시간표, 장비 분류 필터와 선택한 시간 요약
- `/equipment/:id`: 장비 정보와 선택 날짜의 시간표. 첫 화면에서 선택한 장비 상태와 동일한 데이터를 사용한다.
- `/reserve/:id`: 예약 폼
- `/complete/:id`: 예약 완료
- `/schedule`: 운영자용 전체 예약 목록과 복합 필터
- `/lookup`: 예약 ID·취소 토큰을 사용하는 본인 예약 조회와 취소
- 빈 일정, 선택 전, 예약 가능, 예약됨, 충돌, 점검 중, 취소 완료와 서버 실패 상태를 구분한다.

| `id` | 장비를 구분하는 내부 식별자 | UUID 또는 고정 ID |
| `name` | 사용자가 선택할 장비명 | `고온·저온 환경 시험기 1호` |
| `purpose` | 비전문가도 이해할 한 줄 용도 | `온도 변화 환경에서 시료 상태를 확인하는 장비` |
| `location` | 장비가 있는 가상 장소 | `B동 1층` |
| `status` | 현재 예약 가능 여부 | `available`, `maintenance` |
| `notice` | 이용자가 예약 전에 알아야 할 가상 운영 안내 | 점검 기간 또는 준비사항 |

### reservations

| 필드 | 업무 의미 | 형식·예시 |
| --- | --- | --- |
| `id` | 예약을 구분하고 완료 화면에서 사용하는 값 | UUID |
| `equipment_id` | 예약 대상 장비 | `equipment.id` 참조 |
| `requester_name` | 가상 예약자 이름 | `이서연` |

| `purpose` | 장비를 사용하는 이유 | `온도 변화에 따른 가상 시료 상태 확인` |

장비와 예약 데이터는 별도 테이블로 둔다. 예약 시간은 화면에서 한국 시간으로 보여주되 DB에는 타임존이 분명한 값으로 저장한다. 목록 API는 요청 키와 취소 토큰 hash를 반환하지 않는다.

## 9. 업무 규칙과 예외

- 같은 장비에서 `기존 시작 < 신규 종료`이고 `기존 종료 > 신규 시작`이면 중복이다.
- `점검 중` 장비에는 새 예약을 저장하지 않는다.
- 취소된 예약은 중복 계산에서 제외한다.
- 날짜·시간은 한국 시간으로 표시하고 DB에는 명확한 타임존으로 저장한다.
- 실제 임직원 정보와 시험 내용을 사용하지 않는다.

## 13. 기술 및 실행 제약

- 기존 프로젝트라면 현재 기술과 데이터 공급자를 유지한다. 새 프로젝트라면 반응형 웹 화면, 신뢰할 수 있는 쓰기 경계와 영구 저장소를 지원하는 안정적인 구성을 선택한다.
- DB 쓰기와 중복 검사는 사용자 클라이언트가 우회할 수 없는 신뢰 경계에서 수행한다. 비밀값과 관리자 권한은 클라이언트에 두지 않는다.
- 중복 방지는 서버 검사와 DB의 원자적 함수 또는 제약을 함께 사용한다.
- 사용자 계정 대신 가상 사용자명과 서버가 생성한 일회성 취소 토큰을 사용한다.
- 대표 상세·완료 경로의 직접 접근과 예약 API를 함께 확인한다.
- 외부 서비스가 허용되고 요청된 경우 승인된 호스팅과 데이터 공급자를 연결한다. 외부 서비스가 제한되면 로컬 서버와 로컬 저장소에서 같은 흐름을 확인한다.

## 14. 화면 및 디자인 계약

### 14.1 제품 경험의 전제

이 제품은 장비 카탈로그나 기술 사양 대시보드가 아니라, 여러 팀이 공유하는 장비의 시간 충돌을 줄이는 자원 예약 도구다. 첫 화면은 다음 질문에 답해야 한다.

1. 원하는 날짜에 어떤 장비의 어느 시간이 비어 있는가?
2. 예약할 수 없는 시간은 기존 예약 때문인가, 점검 때문인가?
3. 지금 선택한 장비·날짜·시간으로 예약을 진행해도 되는가?

장비 소개보다 가용 시간 비교와 시간 선택을 먼저 제공한다. 장비 카드는 보조 탐색으로 사용할 수 있지만 대표 화면과 예약 시작점이 되어서는 안 된다.

### 14.2 정보 구조

- `장비 일정`: 날짜별 가용 시간표에서 장비와 빈 시간을 선택하는 기본 화면이다.
- `선택한 시간`: 장비·날짜·시간, 위치, 이용 시간과 현재 충돌 여부를 확인한다.
- `예약 정보 입력`: 선택한 일정은 유지하고 예약자·팀·시험 목적만 추가한다.
- `예약 완료`: 예약 ID와 한 번만 제공되는 취소 토큰을 명확히 보여준다.
- `예약 조회·취소`: 예약 ID와 취소 토큰으로 본인 예약을 찾고 취소한다.
- `운영 현황`: 운영자가 선택 날짜의 전체 예약을 목록으로 조회하고 조건을 조합한다.

연구원의 예약 흐름과 운영자의 전체 현황은 서로 다른 목적을 가진다. 운영 현황의 필터와 예약자 정보가 연구원의 첫 화면을 복잡하게 만들지 않게 분리한다.

### 14.3 대표 작업 화면: 장비별 가용 시간표

넓은 화면의 대표 구조는 `날짜와 상태 안내–장비×시간 일정–선택 요약`이다.

1. 날짜 선택
   - 현재 선택 날짜, 이전·다음 날짜와 오늘 이동 행동을 제공한다.
   - 선택한 날짜는 시간표, 선택 요약과 예약 폼에서 동일하게 유지한다.
2. 상태 안내
   - 해당 날짜의 예약 가능 시간 수와 `예약 가능`, `예약됨`, `점검` 범례를 보여준다.
   - 범례는 색상뿐 아니라 텍스트 또는 패턴을 함께 사용한다.
3. 장비×시간 일정
   - 장비를 행, 운영 시간을 열로 배치한다.
   - 장비 정보 열에는 장비명, 위치, 상태 또는 분류를 표시한다.
   - 시간 블록은 최소 30분 단위를 표현할 수 있어야 하며 연속 예약은 하나의 기간으로 이해할 수 있게 연결한다.
   - 예약 가능한 시간 블록만 선택할 수 있다.
4. 선택 요약
   - 선택한 장비명·용도·위치, 날짜, 시작·종료 시간과 이용 시간을 표시한다.
   - `현재 충돌 없음`은 브라우저에서 본 참고 상태이며 제출 시 서버가 다시 확인한다는 사실을 함께 표시한다.
   - 선택이 없을 때는 예약 버튼을 비활성화하고 시간 선택 방법을 안내한다.

### 14.4 시간 선택 규칙

- 사용자는 비어 있는 시작 시간 블록을 선택하고 허용 범위 안에서 종료 시간을 조정할 수 있다.
- 선택 중인 시간은 다른 예약 가능 블록과 분명히 구분하고 시작·종료 시간을 텍스트로 표시한다.
- 기존 예약과 일부라도 겹치는 범위, 운영시간 밖, 30분 미만, 8시간 초과와 점검 시간은 선택 또는 제출할 수 없다.
- 선택 후 장비나 날짜를 바꾸면 이전 선택이 유효한지 다시 확인하고 유효하지 않으면 이유와 함께 선택을 해제한다.
- 시간 충돌 응답을 받으면 사용자가 입력한 예약자 정보는 유지하고 시간표에서 다른 빈 시간을 선택하게 한다.

### 14.5 예약 정보 입력

- 예약 폼은 시간 선택 뒤에만 연다. 사용자가 장비와 시간을 모르는 상태에서 긴 폼부터 작성하게 하지 않는다.
- 폼 상단 또는 옆에 선택한 장비, 날짜와 시간 요약을 고정해 다른 대상을 예약하는 실수를 줄인다.
- 입력 순서는 예약자 이름, 소속 팀, 시험 목적과 이용 수칙 확인이다.
- 시작·종료 시간 수정이 필요하면 폼 안의 복잡한 선택기보다 `시간 다시 선택`으로 일정 화면에 돌아가게 한다.
- 필드 오류는 해당 입력 가까이에 표시하고 서버 충돌과 일반 입력 오류를 구분한다.

### 14.6 예약 완료와 취소 정보

- 완료 화면은 성공 메시지보다 예약한 장비와 이용 일시를 먼저 재확인할 수 있게 한다.
- 예약 ID와 취소 토큰은 별도 코드 영역에 표시하고 한 번에 복사하는 행동을 제공한다.
- 취소 토큰이 다시 표시되지 않는다는 안내를 토큰 가까이에 둔다.
- 완료 화면에서 장비 일정과 예약 조회로 이동할 수 있어야 한다.
- 취소 성공 후 해당 시간 블록은 일정에서 다시 예약 가능한 상태로 갱신한다.

### 14.7 모바일 전환

- 날짜 선택, 예약 가능 시간 수와 장비 분류 필터를 시간표보다 먼저 보여준다.
- 시간표 영역만 좌우로 이동할 수 있으며 전체 페이지에는 가로 스크롤이 생기지 않아야 한다.
- 시간축을 좌우로 이동해도 장비명 열은 화면 왼쪽에 고정한다.
- 시간 블록의 터치 영역은 최소 44px 높이를 확보하고 `가능`, `예약`, `점검` 텍스트를 유지한다.
- 시간을 선택하면 선택 요약과 예약 행동이 시간표 바로 아래에 표시되며 사용자가 긴 표 전체를 지나칠 필요가 없어야 한다.
- 예약 폼은 한 열로 배치하고 날짜·시간 요약을 폼 상단에 유지한다.

### 14.8 시각 체계와 시인성

- 연구 업무에 맞는 밝고 차분한 중립 배경과 녹색 계열의 주요 행동을 사용한다.
- 예약 가능은 옅은 녹색, 예약됨은 중립 회색, 점검은 황색으로 표시하고 모든 블록에 텍스트를 함께 둔다.
- 선택한 시간은 예약 가능 상태보다 높은 대비의 녹색과 체크 아이콘으로 구분한다.
- 장비마다 보조 식별 색상을 사용할 수 있지만 예약 상태 색상과 혼동되지 않게 작은 장비 기호에만 적용한다.
- 장비 원리, 가상의 센서 수치와 시험 결과 차트를 만들지 않는다.

### 14.9 상태와 피드백

- 로딩 중에는 시간표의 행과 열 구조를 유지하는 자리 표시자를 사용해 레이아웃 이동을 줄인다.
- 일정이 비어 있으면 `예약 없음`뿐 아니라 선택 가능한 운영시간을 보여준다.
- 점검 중 장비는 전체 점검인지 일부 시간 점검인지 시간축에서 구분한다.
- 서버 충돌은 다른 예약자의 개인정보 없이 선택한 시간에 예약이 생겼음을 설명하고 시간 다시 선택 행동을 제공한다.
- 예약 제출 중에는 동일 요청의 중복 제출을 막고 성공·실패 후 상태를 명확히 갱신한다.

### 14.10 금지하는 화면 패턴

- 첫 화면을 장비 소개 카드 그리드로만 구성하지 않는다.
- 각 장비의 일정을 별도 상세 페이지에서만 보여줘 여러 장비의 가용 시간을 기억으로 비교하게 만들지 않는다.
- 예약 가능 시간을 `13시 이후 가능` 같은 문장으로만 표현하지 않는다.
- 점검 중 장비에 비활성화된 예약 버튼만 보여주고 점검 범위와 이유를 숨기지 않는다.
- 시간 선택 전에 예약자 정보 폼부터 작성하게 하지 않는다.

### 14.11 UX 수용 기준

- 처음 방문한 사용자가 5초 안에 날짜 선택과 예약 가능한 시간 블록을 찾을 수 있다.
- 한 화면에서 환경 시험기와 충전·방전 시험기의 같은 시간대 가용 여부를 비교할 수 있다.
- 진동 시험기는 모든 점검 시간에서 선택할 수 없고 점검 이유를 확인할 수 있다.
- `13:00~15:00` 선택 후 장비·날짜·시간을 재확인하고 예약 폼으로 진행할 수 있다.
- 모바일에서 장비명 열을 잃지 않고 시간축을 이동해 빈 시간을 선택할 수 있다.
- 주요 본문과 제어 요소는 WCAG AA 수준의 색상 대비를 목표로 하며 예약 상태를 색상만으로 구분하지 않는다.

## 15. 출시 수용 시나리오

### E2E-1. 정상 예약

- Given: 환경 시험기가 사용 가능하고 13:00~15:00가 비어 있다.
- When: 가상 연구원이 해당 시간으로 예약한다.
- Then: 한 건이 저장되고 완료 화면과 일정에 동일하게 표시된다.

### E2E-2. 중복과 점검

- Given: 같은 장비에 13:00~15:00 예약이 있고 진동 시험기는 점검 중이다.
- When: 14:00~16:00 예약 또는 진동 시험기 예약을 시도한다.
- Then: 사유가 표시되고 새 행은 저장되지 않는다.

### E2E-3. 취소와 대상 실행 환경

- Given: 예약 한 건과 완료 화면에서 발급된 올바른 취소 키가 있다.
- When: 대상 실행 환경의 모바일 너비에서 취소한다.
- Then: 상태가 취소로 바뀌고 해당 시간이 다시 예약 가능해진다.

## 16. 위험 요소와 대응

- 동시에 제출되는 중복 예약은 브라우저 검사만 믿지 않고 DB에서 원자적으로 차단한다.
- 취소 토큰은 원문을 DB와 로그에 저장하지 않고 반복 실패를 제한한다.
- 실제 장비 예약에 사용하지 않는 가상 데이터 기반 데모임을 표시한다.

## 17. 범위 잠금

- 반드시 완성: 장비 조회, 일정 조회, 예약 검증·저장, 중복·점검 차단, 취소, 대상 실행 환경 확인.
- 시간이 남으면: 운영 현황의 팀 필터.
- 만들지 않음: 로그인, 승인, 반복 예약, 알림, 실제 장비 연동.

## 18. 완료 정의

- [ ] 정상·중복·점검·잘못된 시간·취소 시나리오가 통과한다.
- [ ] 한 요청이 한 행만 만든다.
- [ ] 첫 화면에서 선택 날짜의 여러 장비 가용 시간을 같은 시간축으로 비교할 수 있다.
- [ ] 예약 가능한 시간 블록 선택이 장비·날짜·시간 요약과 예약 폼으로 이어진다.
- [ ] 점검 중 장비의 시간 블록은 선택할 수 없고 점검 범위를 설명한다.
- [ ] 모바일 시간축을 이동해도 장비명 열과 예약 상태 텍스트를 확인할 수 있다.
- [ ] 모바일 일정과 폼을 사용할 수 있다.
- [ ] 서버 비밀값과 실제 개인정보가 클라이언트·로그·Git에 없다.
- [ ] 대상 실행 환경에서 DB 읽기·쓰기가 확인된다.
