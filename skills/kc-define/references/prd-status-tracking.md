## 1. 제품 개요

전자제품 공장에서 발견된 품질문제를 등록하고 담당 부서·완료 예정일·조치 내용·진행 상태를 관리해 지연과 누락을 줄이는 웹서비스다.

이 제품은 품질관리 전문지식이 없는 사람도 “업무 중 발견된 문제에 담당자와 마감일을 지정하고 해결될 때까지 추적하는 서비스”로 이해할 수 있다. 전자제품 공장을 구체적인 배경으로 사용하지만, 같은 구조는 내부 감사 지적사항, 안전 점검 후속조치, 고객 요청과 일반 프로젝트 이슈 관리에도 적용할 수 있다.

첫 번째 버전에서는 복잡한 품질 승인 체계를 재현하지 않는다. 문제 등록, 담당 부서 배정, 조치 기록, 상태 변경과 지연 확인이라는 핵심 흐름에 집중한다.

## 2. 문제와 배경

### 업무 상황

가상의 전자제품 회사 `다온일렉트로닉스`는 조립, 외관검사, 기능검사와 포장 공정을 거쳐 제품을 출하한다. 여기서 공정은 제품이 완성될 때까지 거치는 작업 단계다. 품질 담당자는 나사 체결 누락, 표면 스크래치, 구성품 누락처럼 정해진 기준과 다른 상태를 발견하면 품질문제로 등록한다.

문제가 등록됐다고 바로 해결되는 것은 아니다. 생산팀은 현장에서 더 이상 불량이 발생하지 않도록 임시 조치를 하고, 생산기술팀이나 설계팀은 원인을 확인하며, 구매품질팀은 공급사 부품 문제를 확인할 수 있다. 품질 담당자는 담당 부서가 무엇을 했는지 확인하고 문제가 다시 발생하지 않도록 최종 조치가 기록됐는지 검토한다.

### 현재 업무 흐름

1. 품질 담당자가 문제를 발견하고 엑셀에 제목·발견일·담당 부서를 적는다.
2. 담당 부서에는 메일이나 메신저로 조치를 요청한다.
3. 담당자는 진행 내용을 별도 문서나 회신에 남긴다.
4. 품질 담당자가 여러 자료를 확인해 엑셀 상태를 갱신한다.
5. 회의 전에 완료 예정일이 지난 항목을 수동으로 색칠한다.
6. 완료 표시가 있어도 어떤 조치를 했는지 찾지 못하는 경우가 생긴다.

이 방식은 누가 최신 정보를 가지고 있는지 불명확하고, 기한이 지난 일을 매번 수동으로 골라야 한다. 상태 이름을 각자 다르게 적으면 `진행 중`, `조치중`, `확인 필요`가 같은 의미인지도 판단하기 어렵다.

### 제품이 바꾸려는 흐름

품질 담당자는 문제를 하나의 서비스에 등록하면서 중요도, 담당 부서와 완료 예정일을 지정한다. 담당 부서는 상세 화면에 원인과 조치 내용을 기록하고 정해진 상태 중 하나로 변경한다. 시스템은 오늘 날짜와 완료 예정일을 비교해 지연 여부를 자동 계산하고, 첫 화면에서 지연 항목을 우선 확인하게 한다. 완료하려면 최종 조치가 반드시 있어야 한다.

### 데이터·운영 제약

실제 회사명, 제품명, 직원명, 고객 정보와 불량 데이터는 사용하지 않는다. 가상 데이터 데모의 공유 쓰기 코드는 쓰기 작업을 무제한 공개하지 않기 위한 최소 장치일 뿐 실제 기업 인증이나 권한 관리가 아니다. 실제 업무 데이터로 전환할 때는 사용자 인증과 부서별 권한을 구현한다.

### 도메인 용어

| 용어 | 이 문서에서의 뜻 |
| --- | --- |
| 품질문제 | 제품이나 작업 결과가 정해진 기준과 다른 상태로 발견된 건이다. |
| 불량 | 품질문제의 대상이 되는 잘못된 제품 상태다. 이 문서에서는 실제 판정 기준을 다루지 않는다. |
| 중요도 | 문제를 얼마나 우선적으로 다뤄야 하는지 나타내는 단순한 단계다. |
| 담당 부서 | 문제 원인 확인과 조치를 맡은 조직이다. 개인 담당자까지 관리하지 않는다. |
| 임시 조치 | 같은 문제가 바로 반복되지 않게 현장에서 먼저 취하는 단기 대응이다. |
| 최종 조치 | 확인한 원인에 대해 재발을 줄이기 위해 완료한 대응 내용이다. |
| 완료 예정일 | 담당 부서가 조치를 마칠 것으로 약속한 날짜다. |
| 지연 | 완료 예정일이 지났지만 상태가 `완료`가 아닌 경우다. |

## 3. 목표와 성공 기준

### 목표

- 품질 담당자가 가상 문제를 등록하고 담당 부서와 기한을 지정한다.
- 담당자가 상태와 조치 내용을 갱신한다.
- 관리자가 지연된 문제를 빠르게 찾는다.

### 성공 기준

- 등록한 문제가 선택한 영구 저장소에 한 번 저장되고 목록에 표시된다.
- 상태·부서·중요도 필터와 지연 판정이 정확하다.
- 조치 내용 없이 `완료`로 변경할 수 없다.

### 비목표

- 제조 품질 시스템, 고객 클레임과 실제 승인 절차를 대체하지 않는다.

## 4. 사용자

| 사용자 | 하려는 일 | 볼 수 있는 정보 | 할 수 없는 일 |
| --- | --- | --- | --- |
| 품질 담당자 | 문제 등록·전체 현황 조회 | 모든 가상 문제와 조치 | 실제 품질 판정 |
| 담당 부서 실무자 | 상태와 조치 내용 갱신 | 배정된 문제를 포함한 목록 | 문제 삭제 |

### 주요 사용자 시나리오

김하늘 품질 담당자는 조립 공정에서 나사 체결 누락이 반복된 것을 확인한다. 문제를 `높음`으로 등록하고 생산기술팀과 일주일 뒤의 완료 예정일을 지정한다. 이후 첫 화면의 `높음` 필터에서 해당 문제를 다시 확인한다.

박도윤 생산기술팀 실무자는 상세 화면에서 원인을 조사 중이라고 기록하고 상태를 `조치 중`으로 변경한다. 임시 조치와 최종 조치를 입력한 뒤 `확인 중`으로 넘기고, 최종 조치가 비어 있는 상태에서 `완료`를 누르면 시스템이 필요한 내용을 안내한다.

이서진 품질 책임자는 주간회의 전에 `지연` 요약 카드를 눌러 완료 예정일이 지난 문제만 확인한다. 숫자 요약과 실제 목록이 항상 같아야 한다.

## 5. 핵심 사용자 흐름

1. 품질 담당자가 `조립 공정 나사 체결 누락`을 등록한다.
2. 중요도, 생산기술팀과 완료 예정일을 지정한다.
3. 담당자가 상세에서 원인과 임시·최종 조치를 기록한다.
4. 상태를 `조치 중`, `확인 중`, `완료`로 변경한다.
5. 관리자가 대시보드에서 지연 항목과 부서별 진행 상태를 확인한다.

## 6. 기능 요구사항

### FR-1. 문제 등록

- 제목, 발견일, 공정, 발견 현상, 중요도, 담당 부서, 완료 예정일과 공유 쓰기 접근 코드를 받는다.
- 제목은 10~80자, 현상은 20~500자로 제한해 지나치게 모호하거나 비어 있는 문제를 막는다.
- 공정·중요도·담당 부서는 준비된 목록에서 선택한다. 자유 입력으로 상태 이름이 늘어나지 않게 한다.
- 완료 예정일은 발견일보다 빠를 수 없다. 브라우저와 서버가 같은 규칙을 검사한다.
- `POST /api/issues`는 유효한 요청을 한 건 저장하고 생성된 ID를 반환한다.
- 수용 조건: 유효한 문제는 목록과 상세에서 동일하게 보이고 잘못된 날짜나 접근 코드는 DB 행을 만들지 않는다.

### FR-2. 목록과 필터

- 기본 목록은 지연 여부와 상관없이 최근 등록 순으로 보여주며 각 행에 제목, 공정, 중요도, 담당 부서, 상태, 완료 예정일과 지연 표시를 제공한다.
- 검색은 제목·현상·공정을 대상으로 하고 상태·부서·중요도·지연 여부 필터와 함께 적용한다.
- 활성 조건과 결과 수를 표시하고 한 번에 초기화한다.
- URL 쿼리에 필터를 반영해 새로고침하거나 링크를 열어도 같은 목록을 볼 수 있게 한다.
- 수용 조건: `생산기술팀`, `높음`, `지연`을 함께 선택하면 세 조건을 모두 만족하는 문제만 나타난다.

### FR-3. 상세와 상태 변경

- 상세 화면은 등록 당시 정보와 현재 조치 정보를 구분한다. 등록 정보에는 제목·발견일·공정·현상·중요도·담당 부서·기한을 표시한다.
- 수정 가능한 조치 정보는 원인, 임시 조치, 최종 조치와 상태다. 원인을 아직 모르면 빈 값으로 둘 수 있지만 `확인 중` 이후에는 원인 또는 원인 미확정 설명이 필요하다.
- `완료`로 바꾸려면 최종 조치가 20자 이상이어야 한다. 상태만 완료로 바꾸고 근거를 비우는 일을 허용하지 않는다.
- `PATCH /api/issues/:id`는 현재 문제 존재 여부, 접근 코드와 상태 규칙을 검사하고 `updated_at`을 갱신한다.
- 저장 중에는 중복 제출을 막고 성공 시 최신 서버 값을 화면에 반영한다. 실패하면 사용자의 입력을 유지한다.
- 수용 조건: 최종 조치 없이 완료 요청은 거절되고, 내용을 입력한 뒤에는 완료와 갱신 시각이 목록에도 반영된다.

### FR-4. 현황 요약

- 첫 화면에는 `전체`, `접수`, `조치 중`, `확인 중`, `지연`, `완료` 건수를 표시한다.
- 수치는 별도 통계 테이블에 저장하지 않고 현재 문제 데이터와 동일한 판정 함수로 계산한다.
- 요약 카드를 누르면 대응하는 필터가 적용되고 목록의 결과 수가 카드 숫자와 일치한다.
- 지연은 상태가 아니라 파생된 조건이므로 완료 상태와 동시에 표시될 수 없다.
- 수용 조건: 지연 문제를 완료 처리하면 새로고침 후 지연 수가 1 감소하고 완료 수가 1 증가한다.

### FR-5. 서버 API

- `GET /api/issues`는 검색·필터·정렬 조건을 받아 화면에 필요한 문제 목록을 반환한다.
- `POST /api/issues`는 신규 문제를 등록하고, `GET /api/issues/:id`는 상세를 반환하며, `PATCH /api/issues/:id`는 조치와 상태를 갱신한다.
- 모든 쓰기는 `x-app-access-code` 헤더 또는 동등한 서버 입력으로 서버에만 저장된 공유 쓰기 코드를 확인한다. 충분히 긴 무작위 코드를 사용하고 반복 실패를 제한하며, 읽기 API에는 비밀값과 내부 오류를 포함하지 않는다.
- API는 사용자가 이해할 오류 코드와 메시지를 반환하되 DB 테이블명, 쿼리와 환경변수 값을 노출하지 않는다.
- 수용 조건: 존재하지 않는 ID는 404, 잘못된 입력은 400, 잘못된 접근 코드는 401 또는 403으로 일관되게 처리한다.

## 7. 화면과 상태

- `/`: 현황 요약, 검색·필터, 문제 목록
- `/issues/new`: 문제 등록
- `/issues/:id`: 상세와 조치 갱신
- 빈 상태, 로딩, 접근 코드 오류, 유효성 오류, DB 실패를 구분한다.

| `discovered_on` | 문제가 처음 발견된 날짜 | 한국 날짜 `YYYY-MM-DD` |
| `process_name` | 문제가 발견된 작업 단계 | `조립`, `포장`, `기능검사` |
| `symptom` | 실제로 관찰된 상태를 판단 없이 설명한 내용 | `검사 표본에서 고정 나사 1개가 없음` |
| `severity` | 처리 우선순위를 위한 단순 중요도 | `low`, `medium`, `high` |
| `owner_department` | 원인 확인과 조치를 맡은 가상 부서 | `생산기술팀` |
| `due_on` | 조치 완료를 목표로 하는 날짜 | 발견일과 같거나 이후 |
| `status` | 현재 진행 단계 | `received`, `in_progress`, `verifying`, `completed` |
| `cause` | 확인한 원인 또는 원인 미확정 설명 | 빈 값 허용 |
| `temporary_action` | 당장 반복을 줄이기 위한 임시 대응 기록 | 빈 값 허용 |
| `final_action` | 완료를 위해 필요한 최종 조치 기록 | 완료 시 20자 이상 |
| `created_at` | 처음 등록된 시각 | 서버 생성 시각 |
| `updated_at` | 가장 최근 갱신 시각 | 서버 갱신 시각 |

`지연`은 별도 DB 필드로 저장하지 않는다. 한국 날짜 기준 오늘이 `due_on`보다 늦고 `status`가 `completed`가 아닐 때 화면과 API에서 계산한다. 이렇게 해야 날짜가 바뀌어도 별도 배치 작업 없이 지연 상태가 정확하게 바뀐다.

## 9. 업무 규칙과 예외

- 상태는 `접수`, `조치 중`, `확인 중`, `완료`만 사용한다.
- 중요도는 `낮음`, `보통`, `높음`이다.
- 오늘이 완료 예정일보다 늦고 상태가 완료가 아니면 `지연`이다.
- 완료 예정일은 발견일보다 빠를 수 없다.
- 완료 변경에는 최종 조치가 필수다.
- 삭제 기능은 제공하지 않는다.

## 13. 기술 및 실행 제약

- 기존 프로젝트라면 현재 기술과 데이터 공급자를 유지한다. 새 프로젝트라면 반응형 웹 화면, 서버 측 쓰기 경계와 영구 저장소를 지원하는 안정적인 구성을 선택한다.
- 접근 코드, 데이터 자격증명과 관리자 권한은 사용자 클라이언트 밖에 둔다.
- 지연 여부는 저장하지 않고 한국 날짜 기준으로 계산한다.
- 실제 직원명·제품명·회사명을 사용하지 않는다.
- `/issues/new`, `/issues/:id` 직접 접근과 문제 API를 함께 확인한다.
- 외부 서비스가 허용되고 요청된 경우 승인된 호스팅과 데이터 공급자를 연결한다. 외부 서비스가 제한되면 로컬 서버와 로컬 저장소에서 같은 흐름을 확인한다.

## 14. 화면 및 디자인 계약

### 14.1 제품 경험의 전제

이 제품은 품질 성과를 보고하는 경영 대시보드가 아니라, 발견된 문제에 책임과 기한을 부여하고 조치가 끝날 때까지 운영하는 작업 대기함이다. 첫 화면은 다음 질문에 답해야 한다.

1. 지금 기한을 넘겼거나 우선 조치가 필요한 문제는 무엇인가?
2. 누가 어느 부서에서 언제까지 처리해야 하는가?
3. 문제를 닫기 위해 아직 부족한 원인·조치 정보는 무엇인가?

전체 건수와 완료율보다 지연, 담당 미지정, 높은 중요도와 가까운 완료 예정일을 먼저 식별할 수 있게 한다.

### 14.2 정보 구조

- `조치 대기함`: 완료되지 않은 문제를 책임과 기한 중심으로 조회하는 기본 화면이다.
- `기한 지연`: 완료 예정일이 지났지만 완료되지 않은 문제만 보여주는 파생 목록이다.
- `내 담당`: 현재 사용자에게 배정된 문제를 보여준다.
- `완료`: 최종 조치가 기록되고 완료된 문제를 조회한다.
- `문제 등록`: 발견 내용, 중요도, 담당 부서와 완료 예정일을 지정한다.
- `문제 상세`: 등록 당시 정보와 이후 개선조치 정보를 구분해 조회·갱신한다.

`지연`은 사용자가 직접 선택하는 업무 상태가 아니다. 현재 날짜, 완료 예정일과 완료 여부에서 계산된 파생 조건이며 `접수`, `조치 중`, `확인 중` 상태 위에 별도 경고로 표시한다.

### 14.3 대표 작업 화면: 조치 대기함

넓은 화면의 기본 구조는 `업무 탐색–우선 확인 영역–문제 표`다.

1. 업무 탐색
   - 조치 대기함, 기한 지연, 내 담당과 완료 목록을 제공한다.
   - `품질문제 등록`은 어느 목록에서도 찾을 수 있는 명확한 주요 행동으로 둔다.
2. 우선 확인 영역
   - 기한 지연, 아직 접수, 조치 진행과 담당 미지정 건수를 표시한다.
   - 각 항목은 단순 통계 카드가 아니라 누르면 같은 조건의 실제 목록으로 이동하는 필터 역할을 한다.
   - 지연 항목을 첫 번째에 배치하고 경고색, 텍스트와 초과 건수를 함께 사용한다.
3. 검색과 필터
   - 문제 번호·제목·공정 검색, 상태와 담당 부서 필터를 제공한다.
   - 적용 결과 수와 정렬 기준을 문제 표 바로 위에 표시한다.
4. 문제 표
   - 문제 번호·제목·공정, 중요도, 담당자·부서, 업무 상태, 완료 예정일과 지연 일수를 표시한다.
   - 기본 정렬은 PRD의 업무 규칙을 따르되 지연 화면에서는 초과 일수가 큰 항목을 먼저 검토할 수 있게 한다.

### 14.4 목록과 요약의 일관성

- 우선 확인 영역의 수치는 현재 문제 데이터와 목록에서 사용하는 동일한 판정 함수로 계산한다.
- 요약 항목을 선택하면 해당 필터가 적용되고 화면의 결과 수가 선택한 숫자와 일치해야 한다.
- 검색과 상태·부서·중요도·지연 필터는 동시에 적용할 수 있으며 활성 조건을 확인하고 한 번에 초기화할 수 있어야 한다.
- 지연 문제를 완료하면 지연 수가 감소하고 완료 수가 증가한 결과가 목록과 탐색에 동시에 반영되어야 한다.

### 14.5 문제 상세와 개선조치

기본 대기함을 열었을 때 첫 번째 문제 상세를 자동으로 덮어씌우지 않는다. 사용자가 문제 행을 선택하면 넓은 화면에서는 오른쪽 패널, 모바일에서는 독립 상세 화면으로 연다.

상세는 다음 순서로 구성한다.

1. 문제 번호, 업무 상태, 중요도·공정과 제목
2. 지연 여부와 초과 일수. 지연일 때만 강하게 표시한다.
3. 담당 부서, 담당자와 완료 예정일
4. 등록 당시 발견 현상
5. 원인 조사, 임시 조치, 최종 조치와 업무 상태를 갱신하는 개선조치 영역
6. 문제 등록, 담당 배정과 변경 시각을 보여주는 처리 이력

등록 당시 발견 현상은 읽기 전용 영역으로, 이후 작성하는 원인·조치 내용은 수정 영역으로 시각적으로 구분한다. `완료`를 선택했지만 최종 조치가 20자 미만이면 저장 행동 가까이에 이유와 수정 방법을 표시한다.

### 14.6 문제 등록 화면

- 등록 폼은 `발견 내용`과 `조치 책임` 두 묶음으로 나눈다.
- 발견 내용에는 제목, 공정, 중요도와 관찰한 현상을 배치한다.
- 조치 책임에는 담당 부서와 완료 예정일을 배치한다.
- 필드 순서는 사용자가 문제를 설명한 뒤 책임과 기한을 지정하는 업무 순서를 따른다.
- 오류는 해당 필드 가까이에 표시하고 제출 실패 시 입력 내용을 유지한다.
- 등록 성공 후 새 문제를 목록과 결과 수에 반영하고 생성된 문제를 열 수 있게 한다.

### 14.7 모바일 전환

- 좌측 업무 탐색은 상단의 간결한 네 개 목록 전환으로 바꾼다.
- 우선 확인 영역은 두 열 카드로 배치하되 지연 건수와 의미를 첫 화면에서 읽을 수 있어야 한다.
- 넓은 화면의 문제 표는 모바일에서 문제 카드로 변환한다.
- 모바일 문제 카드는 제목, 상태, 중요도, 담당자와 완료 예정일을 한 화면에 보여준다.
- 문제를 선택하면 목록 위에 상세를 겹쳐 보여주지 않고 전체 너비 상세 화면으로 전환하며 목록 복귀 행동을 제공한다.

### 14.8 시각 체계와 시인성

- 중립적인 밝은 작업 영역과 짙은 업무 탐색 영역을 사용해 목록과 탐색의 경계를 분명히 한다.
- 파란색은 선택과 주요 행동, 적색은 지연과 저장을 막는 오류, 황색은 확인 중, 녹색은 완료에 사용한다.
- 중요도와 상태는 색상, 텍스트와 필요할 때 아이콘을 함께 사용한다.
- 표의 열 제목과 값 정렬을 일관되게 유지하고 제목이 아닌 보조 메타정보는 한 단계 낮은 대비로 표시한다.
- 높은 중요도와 지연을 같은 의미처럼 표현하지 않는다. 중요도는 업무 영향, 지연은 기한 초과다.

### 14.9 금지하는 화면 패턴

- 문제 목록보다 장식용 차트와 완료율 그래프를 먼저 보여주지 않는다.
- 실제 데이터에서 계산할 수 없는 품질 점수, 생산성 KPI와 추세를 만들지 않는다.
- 지연을 사용자가 선택하거나 저장하는 다섯 번째 업무 상태처럼 만들지 않는다.
- 발견 현상, 원인과 조치를 하나의 긴 메모 필드로 합치지 않는다.
- 담당자와 완료 예정일을 상세 안에만 숨겨 목록에서 책임과 기한을 비교할 수 없게 하지 않는다.

### 14.10 UX 수용 기준

- 처음 방문한 사용자가 5초 안에 지연 건수와 문제 등록 행동을 찾을 수 있다.
- 지연 요약을 선택했을 때 목록 결과 수와 요약 숫자가 일치한다.
- 문제 목록만 보고 문제 제목, 중요도, 담당자·부서, 상태와 완료 예정일을 비교할 수 있다.
- 상세에서 등록 당시 현상과 이후 개선조치 입력 영역을 혼동하지 않는다.
- 모바일에서 지연 목록 선택, 문제 상세 확인, 조치 입력과 목록 복귀를 가로 스크롤 없이 완료한다.
- 주요 본문과 제어 요소는 WCAG AA 수준의 색상 대비를 목표로 하며 상태와 중요도를 색상만으로 구분하지 않는다.

## 15. 출시 수용 시나리오

### E2E-1. 등록과 조회

- Given: 올바른 접근 코드가 있다.
- When: 나사 체결 누락 문제를 등록한다.
- Then: 한 건이 저장되고 목록·상세·전체 건수에 반영된다.

### E2E-2. 지연과 완료 규칙

- Given: 완료 예정일이 지난 미완료 문제가 있다.
- When: 지연 필터를 적용하고 최종 조치 없이 완료를 시도한다.
- Then: 지연 목록에 나타나고 완료 변경은 거절된다.

### E2E-3. 정상 완료

- Given: 조치 중 문제가 있다.
- When: 최종 조치를 입력하고 완료로 변경한다.
- Then: 지연 표시가 사라지고 완료 수가 증가한다.

### E2E-4. 대상 실행 환경

- Given: 대상 실행 환경을 모바일 너비로 열었다.
- When: 목록·필터·등록·상태 변경을 수행한다.
- Then: 핵심 행동이 가능하고 서버 비밀값이 노출되지 않는다.

## 16. 위험 요소와 대응

- 클라이언트 수치를 별도 저장하지 않고 목록 데이터에서 계산해 불일치를 막는다.
- 상태 변경은 서버가 현재 값과 업무 규칙을 검증한 뒤 수행한다.
- 공유 쓰기 접근 코드는 실제 기업 인증을 대체하지 않는다고 표시한다.

## 17. 범위 잠금

- 반드시 완성: 등록, 목록·검색·필터, 상세, 상태·조치 변경, 지연 판정, 요약, 대상 실행 환경 확인.
- 시간이 남으면: 중요도별 정렬.
- 만들지 않음: 인증, 파일, 댓글, 알림, 승인, AI, 예측 차트.

## 18. 완료 정의

- [ ] 등록·조회·필터·갱신이 실제 DB에서 동작한다.
- [ ] 지연과 완료 규칙이 경계 날짜에서 정확하다.
- [ ] 잘못된 입력과 접근 코드가 저장 전에 차단된다.
- [ ] 요약 수치와 목록이 일치한다.
- [ ] 첫 화면에서 지연·담당 미지정과 완료 예정일을 문제 목록보다 늦지 않게 확인할 수 있다.
- [ ] 지연은 저장 상태가 아니라 완료 예정일과 완료 여부에서 계산된 조건으로 일관되게 표시된다.
- [ ] 문제 상세에서 등록 당시 발견 현상과 이후 개선조치 입력 영역이 구분된다.
- [ ] 대상 실행 환경의 모바일 너비에서 핵심 시나리오가 통과한다.
- [ ] 실제 회사 데이터와 비밀값이 코드·로그·Git에 없다.

## 19. 가정과 미결정 사항

- 단일 공장과 한국 날짜를 기준으로 한다.
- 가상 데이터 데모 범위에서는 서버에만 저장된 공유 쓰기 코드 하나를 사용한다. 실제 업무 데이터에는 이 가정을 적용하지 않는다.
