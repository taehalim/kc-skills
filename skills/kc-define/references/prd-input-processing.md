## 1. 제품 개요

자동차 부품 회사의 구매 담당자가 두 공급사의 가상 견적을 입력해 누락 품목, 수량·단가 차이와 총액을 비교하고 결과를 저장하는 웹서비스다. 구매 결정을 대신하지 않고 검토할 차이를 빠르게 드러낸다.

이 제품은 자동차 부품 지식이 없는 사람도 “같은 물건 목록을 두 업체가 각각 얼마에 공급하겠다고 제안했는지 비교하는 도구”로 이해할 수 있다. 자동차 부품 회사를 구체적인 배경으로 사용하지만, 같은 구조는 총무팀의 사무용품 견적, 마케팅팀의 행사 대행 견적, IT팀의 장비 구매 견적에도 적용할 수 있다.

이번 버전은 문서 파일을 자동으로 읽지 않는다. 사용자가 정리된 품목 행을 입력하거나 준비된 샘플을 불러오고, 시스템은 명확한 품목 코드를 기준으로 차이를 계산한다. 이를 통해 파일 처리나 AI 매칭보다 업무 규칙과 검증 결과에 집중한다.

## 2. 문제와 배경

### 업무 상황

가상의 자동차 부품 회사 `가온모빌리티` 구매팀은 신규 생산라인에 필요한 부품을 공급사 두 곳에 요청했다. 구매팀은 요청한 품목 코드와 수량을 전달하고, 공급사는 공급 가능한 품목·수량·단가를 담은 견적을 회신한다. 여기서 공급사는 부품이나 서비스를 납품하겠다고 제안하는 외부 업체이며, 견적은 어떤 품목을 몇 개, 개당 얼마에 제공할지를 적은 문서다.

두 견적은 표의 순서가 다를 수 있다. 한 업체는 요청 품목을 빠뜨릴 수 있고, 다른 업체는 별도의 포장 자재를 추가할 수도 있다. 같은 품목이라도 공급 가능한 수량이나 단가가 다를 수 있다. 담당자가 총액만 비교하면 특정 품목이 누락돼 총액이 낮아진 것인지, 실제로 단가가 낮은 것인지 알 수 없다.

### 현재 업무 흐름

1. 담당자가 두 업체의 견적서를 각각 연다.
2. 품목 코드나 품목명을 눈으로 찾아 같은 행끼리 맞춘다.
3. 한쪽에 없는 품목을 별도로 표시한다.
4. 수량과 단가를 비교하고 계산기로 품목 금액과 총액을 다시 계산한다.
5. 차이를 엑셀이나 메일에 정리해 검토자에게 전달한다.
6. 수정 견적이 오면 같은 작업을 다시 반복한다.

품목이 많을수록 행을 잘못 맞추거나 누락을 놓칠 가능성이 커진다. 특히 이름이 비슷한 부품을 자동으로 같은 품목이라고 판단하면 더 위험하다. 예를 들어 `센서 커넥터 A형`과 `센서 커넥터 B형`은 글자가 비슷해도 호환되지 않을 수 있다.

### 제품이 바꾸려는 흐름

사용자는 공급사 A와 B의 품목을 구조화된 표에 입력한다. 시스템은 사람이 확인한 품목 코드가 정확히 같은 행만 연결하고, 누락 방향과 수량·단가 차이를 계산한다. 사용자는 차이가 있는 항목을 우선 검토한 뒤 비교 결과를 저장하고 나중에 동일한 원본으로 재현한다.

### 데이터·운영 제약

실제 공급사명, 부품 가격과 회사 견적은 기밀일 수 있으므로 모두 가상 데이터로 대체한다. OCR, PDF, 엑셀 업로드를 제외하는 이유는 기술적으로 불가능해서가 아니라 첫 번째 버전에서 파일 형식 문제보다 비교 규칙과 결과 검증을 우선하기 위해서다.

### 도메인 용어

| 용어 | 이 문서에서의 뜻 |
| --- | --- |
| 구매팀 | 회사가 필요한 물품과 서비스를 외부 업체에서 조달하는 부서다. |
| 공급사 | 회사에 부품이나 서비스를 납품하겠다고 제안하는 업체다. |
| 견적 | 공급 품목, 수량, 단가와 금액을 제시한 문서 또는 데이터다. |
| 품목 코드 | 서로 다른 문서에서도 같은 부품을 구분하기 위해 사용하는 고유한 문자·숫자 조합이다. |
| 단가 | 품목 한 개당 가격이다. |
| 품목 금액 | 수량에 단가를 곱한 금액이다. |
| 누락 품목 | 한 공급사 견적에는 있지만 다른 견적에는 없는 품목이다. |

## 3. 목표와 성공 기준

### 목표

- 품목 코드로 두 견적을 정확히 맞춘다.
- 누락·수량 차이·단가 차이를 구분한다.
- 원본 입력과 결과를 저장해 다시 검토한다.

### 성공 기준

- 샘플 견적의 모든 차이와 총액이 수동 계산 결과와 일치한다.
- 잘못된 입력은 비교와 저장 전에 차단된다.
- 저장한 결과를 다시 열었을 때 같은 비교가 재현된다.

### 비목표

- 공급사를 추천하거나 발주·승인을 자동화하지 않는다.

## 4. 사용자

| 사용자 | 하려는 일 | 볼 수 있는 정보 | 할 수 없는 일 |
| --- | --- | --- | --- |
| 구매 담당자 | 견적 입력·비교·저장 | 두 공급사의 가상 품목과 차이 | 자동 구매 결정 |
| 구매 검토자 | 저장 결과 재확인 | 원본 입력·총액·차이 | 원본 견적 대체 |

### 주요 사용자 시나리오

정유진 구매 담당자는 신규 생산라인 부품 견적 두 개를 받았다. 공급사 A의 견적에는 센서 커넥터가 있지만 공급사 B에는 없고, 공급사 B에는 포장 트레이가 추가되어 있다. 유진은 샘플을 불러와 비교를 실행하고 `A에만 있음`, `B에만 있음`, `수량·단가 차이`를 차례로 검토한다.

강민석 구매 검토자는 저장 이력에서 해당 비교를 다시 연다. 총액 차이만 보는 대신 어떤 품목이 차이를 만들었는지 확인하고, 실제 업무라면 원본 견적서와 다시 대조한다. 서비스는 어느 공급사를 선택하라고 추천하지 않는다.

## 5. 핵심 사용자 흐름

1. 사용자가 비교 이름과 공급사 A·B를 입력한다.
2. 샘플 견적을 불러오거나 품목 행을 입력한다.
3. 입력 오류를 수정하고 비교한다.
4. 누락·수량·단가 차이와 총액을 확인한다.
5. 접근 코드를 입력해 결과를 저장하고 이력에서 다시 연다.

## 6. 기능 요구사항

### FR-1. 견적 입력

- 비교 이름과 공급사 A·B의 가상 이름을 먼저 입력한다. 두 공급사 이름이 같으면 구분할 수 있도록 수정 안내를 제공한다.
- 각 견적에서 품목 코드, 품목명, 수량과 단가 행을 추가·수정·삭제한다. 최소 한 행이 있어야 비교할 수 있다.
- 품목 코드는 앞뒤 공백을 제거하고 영문은 대문자로 정규화하지만 사용자에게 입력한 품목명을 임의로 바꾸지 않는다.
- 빈 필드, 같은 견적 안의 중복 코드, 정수가 아닌 수량, 0 이하 수량·단가를 해당 행에서 안내한다.
- `샘플 불러오기`는 현재 입력을 바꾸기 전에 확인하고 문서의 가상 견적을 정확히 채운다.
- 수용 조건: 한 행을 추가·수정·삭제해도 다른 공급사 입력은 유지되며 잘못된 행이 있으면 비교 버튼이 실행되지 않는다.

### FR-2. 품목 매칭과 계산

- 정규화한 품목 코드가 같은 행만 하나의 비교 행으로 묶는다. 품목명 유사도는 사용하지 않는다.
- 한쪽에만 있는 코드는 해당 공급사 값만 보여주고 다른 쪽에는 `견적에 없음`을 표시한다.
- 품목 금액은 수량×단가, 공급사 총액은 해당 견적의 모든 품목 금액 합으로 계산한다.
- 결과 상태는 `동일`, `수량 차이`, `단가 차이`, `수량·단가 차이`, `A에만 있음`, `B에만 있음` 중 하나다.
- 계산 함수는 화면과 분리된 순수 함수로 작성해 샘플 정답을 자동 테스트할 수 있어야 한다.
- 수용 조건: 입력 행 순서를 바꿔도 같은 품목 코드의 결과와 총액이 달라지지 않는다.

### FR-3. 결과 탐색

- 결과 상단에 공급사별 총액과 절대 차액을 표시한다. 차액이 낮은 공급사가 더 좋은 선택이라는 문구는 만들지 않는다.
- 사용자는 `전체`, `누락`, `수량 차이`, `단가 차이` 필터로 검토 대상을 좁힌다.
- 각 비교 행에는 두 공급사의 수량·단가·품목 금액과 판정 근거를 함께 표시한다.
- 입력으로 돌아가 값을 수정하면 이전 결과가 현재 입력과 다르다는 상태를 표시하거나 즉시 재계산한다. 오래된 결과를 최신인 것처럼 보여주지 않는다.
- 수용 조건: `누락` 필터에서 `CON-440`, `TRY-660`만 보이고 누락 방향이 서로 다르게 표시된다.

### FR-4. 저장과 조회

- 저장은 유효한 비교를 완료한 뒤에만 가능하다. 가상 데이터 데모에서는 사용자가 서버에만 저장된 공유 쓰기 코드를 입력하고 저장 행동을 확인한다. 실제 견적을 다루는 제품으로 전환할 때는 사용자 인증과 권한을 별도로 구현한다.
- `POST /api/comparisons`는 브라우저 계산 결과를 신뢰하지 않고 원본 입력을 다시 검증한 뒤 비교 메타정보와 품목 행을 하나의 작업으로 저장한다.
- 일부 품목만 저장되는 일이 없도록 비교와 품목 저장은 트랜잭션 또는 동등한 원자적 처리로 수행한다.
- `GET /api/comparisons`는 이름, 공급사, 생성 시각과 품목 수를 반환하고, `GET /api/comparisons/:id`는 원본 행을 반환한다.
- 상세 화면은 저장된 결과값을 그대로 믿지 않고 같은 비교 함수로 다시 계산한다.
- 수용 조건: 저장된 상세의 원본 행 수와 입력 행 수가 같고, 다시 계산한 상태·총액이 저장 직전 화면과 일치한다.

## 7. 화면과 상태

- `/`: 새 비교와 저장 이력
- `/compare`: 두 견적 입력과 결과
- `/history`: 저장 목록
- `/history/:id`: 저장 상세
- 빈 입력, 행 오류, 저장 중, 접근 코드 오류, DB 실패를 구분한다.

결과는 원본 항목으로 다시 계산하며 중복 저장하지 않는다.

DB에는 브라우저가 계산한 총액과 판정 상태를 저장하지 않는다. 계산 규칙이 수정되더라도 원본 견적에서 결과를 다시 만들 수 있도록 비교 이름과 두 공급사의 원본 행을 보존한다. API 응답은 접근 코드와 서버 환경변수를 포함하지 않는다.

## 9. 업무 규칙과 예외

- 같은 견적 안에서 품목 코드는 중복될 수 없다.
- 금액은 부가세 포함 원화 정수로 계산한다.
- 품목명이 비슷해도 코드가 다르면 자동으로 합치지 않는다.
- 결과에는 `구매 결정 전 원본 견적서를 확인하세요`를 표시한다.

## 13. 기술 및 실행 제약

- 계산은 클라이언트의 단일 순수 함수로 구현하고 테스트한다.
- 접근 코드, 데이터 자격증명과 관리자 권한은 사용자 클라이언트 밖에 둔다. 공유 쓰기 코드는 충분히 긴 무작위 값으로 만들고 반복 실패를 제한한다.
- `/history/:id` 직접 접근과 저장 API를 함께 확인한다.
- 외부 서비스가 허용되고 요청된 경우 승인된 호스팅과 데이터 공급자를 연결한다. 외부 서비스가 제한되면 로컬 서버와 로컬 저장소에서 같은 흐름을 확인한다.

## 14. 화면 및 디자인 계약

### 14.1 제품 경험의 전제

이 제품은 공급사를 평가하거나 더 저렴한 견적을 추천하는 대시보드가 아니라, 두 원본 견적을 행 단위로 대조해 사람이 검토할 차이를 빠르게 찾는 문서 검토 도구다. 사용자는 비교 과정에서 다음 질문에 답할 수 있어야 한다.

1. 양쪽 견적에서 빠진 품목은 무엇이며 어느 공급사에 없는가?
2. 같은 품목 코드에서 수량과 단가 중 무엇이 다른가?
3. 화면의 판정은 어떤 원본 값에서 나온 것인가?

총액은 중요한 요약이지만 검토의 시작점이 아니다. 누락과 행 단위 차이가 총액보다 먼저 발견되도록 시각적 계층을 구성한다.

### 14.2 정보 구조와 작업 단계

- `기본 정보`: 비교 이름과 공급사 A·B를 지정한다.
- `견적 입력`: 두 공급사의 원본 행을 추가·수정·삭제하고 입력 오류를 해결한다.
- `차이 검토`: 누락, 수량 차이, 단가 차이, 양쪽 금액과 판정 근거를 검토한다.
- `저장 이력`: 과거 비교의 이름, 공급사, 품목 수, 차이 수와 저장 시각을 확인하고 원본 행을 다시 연다.
- `이용 안내`: 품목 코드 기준 매칭과 자동 추천을 하지 않는 범위를 설명한다.

새 비교는 위 세 단계를 순서대로 진행한다. 저장 이력에서 기존 비교를 열면 입력 단계를 반복하지 않고 차이 검토 화면을 먼저 보여주되, 언제든 원본 입력으로 돌아갈 수 있어야 한다.

### 14.3 단계 탐색과 진행 상태

- 넓은 화면에서는 현재 비교 문서 ID, 저장 상태와 세 단계를 고정된 작업 탐색 영역에 표시한다.
- 각 단계는 번호, 이름과 현재 데이터 요약을 함께 보여준다. 예: `견적 입력 · A 5행 / B 5행`.
- 완료한 단계, 현재 단계와 아직 완료하지 않은 단계를 색상 외에 아이콘·번호·텍스트로 구분한다.
- 단계 이동은 사용자의 입력을 임의로 삭제하지 않는다.
- 잘못된 입력이 남아 있으면 차이 검토 단계로 이동하지 못하며 오류가 있는 행으로 사용자를 안내한다.

### 14.4 견적 입력 화면

넓은 화면에서는 공급사 A와 B의 입력 표를 좌우에 나란히 배치한다. 두 표는 같은 열 구조와 밀도를 사용한다.

- 각 공급사 영역 상단에 공급사 이름, 품목 수, 행 추가 행동을 표시한다.
- 각 행에는 품목 코드, 품목명, 수량, 단가와 삭제 행동을 표시한다.
- 행 오류는 표 상단의 공통 메시지만으로 설명하지 않고 문제가 있는 입력값 가까이에 표시한다.
- 공급사별 총액은 각 입력 표의 하단에서 확인할 수 있지만 입력 완료 행동보다 강조하지 않는다.
- 샘플 불러오기는 현재 입력을 교체한다는 사실을 행동 전에 명확히 알린다.

모바일에서는 A와 B 표를 억지로 같은 너비에 축소하지 않는다. 공급사 A 입력을 먼저, 공급사 B 입력을 다음 순서로 배치하고 각 공급사의 제목을 스크롤 중에도 구분할 수 있게 한다.

### 14.5 차이 검토 대표 화면

차이 검토가 이 제품의 대표 작업 화면이다. 다음 순서로 정보를 배치한다.

1. 비교 이름과 `입력 수정`, `비교 저장` 행동
2. 확인할 전체 차이 수와 누락·수량·단가 차이의 요약
3. 공급사별 총액과 절대 차액. 이 영역에는 `선택 추천 아님`을 표시한다.
4. `차이만`, `누락`, `수량`, `단가`, `전체` 필터
5. 품목별 비교 행

품목별 비교 행은 다음 열 구조를 사용한다.

- 품목 코드와 품목명
- 공급사 A의 수량·단가·품목 금액
- 공급사 B의 수량·단가·품목 금액
- 판정과 판정 근거

한쪽에 품목이 없으면 빈 셀이나 `-` 대신 `견적에 없음`과 누락 방향을 표시한다. 수량 또는 단가가 다르면 서로 다른 값과 절대 차이를 같은 행에서 확인할 수 있어야 한다.

### 14.6 모바일 비교 방식

- 모바일에서는 열 너비를 축소해 데스크톱 표 전체를 맞추지 않는다.
- 각 품목을 하나의 비교 카드로 전환하고 `품목 정보 → 공급사 A → 공급사 B → 판정 근거` 순서로 표시한다.
- 누락 방향과 판정은 카드를 열거나 좌우로 이동하지 않아도 확인할 수 있어야 한다.
- 비교 필터는 가로로 잘리지 않게 스크롤 또는 동일 너비 버튼으로 제공한다.
- 입력 수정과 비교 저장은 서로 다른 행동임을 알 수 있도록 같은 강조 수준을 사용하지 않는다. 저장을 주요 행동으로 둔다.

### 14.7 시각 체계와 시인성

- 문서와 표를 오래 검토하는 업무에 맞게 밝은 배경, 선명한 본문과 절제된 구분선을 사용한다.
- 파란색 계열은 현재 단계와 선택 상태, 황색은 검토가 필요한 값, 적색은 누락과 유효성 오류에 사용한다.
- 통화, 수량, 품목 코드는 숫자 자릿수와 행 정렬을 비교하기 쉬운 형태로 표시한다.
- 같은 의미의 수량·단가·금액은 두 공급사 영역에서 같은 위치와 서체 계층을 사용한다.
- 상태와 판정은 색상뿐 아니라 `A에만 있음`, `수량 차이` 같은 텍스트를 항상 함께 표시한다.

### 14.8 상태와 피드백

- 입력이 변경되어 기존 결과가 오래된 상태가 되면 결과를 최신인 것처럼 유지하지 않는다. 재계산 또는 `입력 변경됨` 안내를 제공한다.
- 필터를 적용하면 표시 행 수와 필터 이름을 함께 갱신한다.
- 저장 중, 저장 완료, 접근 코드 오류와 서버 실패를 서로 다른 메시지로 제공하고 입력 내용은 유지한다.
- 저장 이력 상세는 저장된 결과값을 그대로 출력하지 않고 원본 행을 다시 계산했다는 사실을 사용자에게 설명할 수 있어야 한다.

### 14.9 금지하는 화면 패턴

- 총액이 낮은 공급사를 승자, 추천 또는 점수로 표현하지 않는다.
- 공급사별 값을 서로 떨어진 카드나 별도 페이지에 배치해 사용자가 기억으로 비교하게 만들지 않는다.
- 누락, 수량과 단가 차이를 하나의 모호한 `불일치` 상태로 합치지 않는다.
- 원본 값 없이 차액이나 비율만 보여주지 않는다.
- 비교 업무와 무관한 원형 차트, 추세 그래프와 공급사 KPI를 만들지 않는다.

### 14.10 UX 수용 기준

- 처음 보는 사용자가 5초 안에 현재 단계와 다음 행동을 설명할 수 있다.
- `누락` 필터를 한 번 선택해 `CON-440`, `TRY-660`과 서로 다른 누락 방향을 확인할 수 있다.
- `CAB-210` 한 행에서 양쪽 수량·단가·금액과 판정 근거를 동시에 확인할 수 있다.
- 모바일에서 한 품목의 A·B 값과 판정을 가로 페이지 스크롤 없이 검토할 수 있다.
- 주요 본문과 입력 요소는 WCAG AA 수준의 색상 대비를 목표로 하며 판정은 색상만으로 구분하지 않는다.

## 15. 출시 수용 시나리오

### E2E-1. 비교

- Given: 문서의 A·B 샘플이 입력되어 있다.
- When: 비교를 실행한다.
- Then: `CON-440`과 `TRY-660`의 누락 방향, `CAB-210`의 수량·단가 차이, 각 총액이 정확하다.

### E2E-2. 잘못된 입력

- Given: 중복 코드와 수량 0인 행이 있다.
- When: 비교를 실행한다.
- Then: 해당 행의 수정 안내가 보이고 비교와 저장은 일어나지 않는다.

### E2E-3. 저장과 조회

- Given: 유효한 결과와 올바른 접근 코드가 있다.
- When: 저장하고 상세를 다시 연다.
- Then: 원본과 재계산 결과가 동일하고 비밀값은 노출되지 않는다.

## 16. 위험 요소와 대응

- 잘못된 자동 매칭을 피하기 위해 품목 코드만 신뢰한다.
- 부동소수점 오류를 피하기 위해 원 단위 정수를 사용한다.
- 저장 API가 준비되지 않으면 비교 기능을 먼저 완성하되 최종 PRD 완료로 표시하지 않는다.

## 17. 범위 잠금

- 반드시 완성: 입력, 검증, 정확 매칭, 차이·총액 계산, 저장·조회, 대상 실행 환경 확인.
- 시간이 남으면: 차이 항목만 보기.
- 만들지 않음: 파일 업로드, OCR, AI, 세금, 추천, 발주.

## 19. 가정과 미결정 사항

- 품목 코드는 공급사와 구매팀이 합의한 값이라고 가정한다.
- 단일 비교에는 공급사 두 곳만 포함한다.
